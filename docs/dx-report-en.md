# RWA Radar × Binance Web3 API: a developer experience report

*RWA Radar — tokenized-stock anomaly monitor, BNB Hackathon*

This isn't going to read like a press release. Short version: the signing setup is rock solid once you've been burned by it once, and the actual time sinks were never the cryptography — they were two or three spots where the docs don't quite match reality, and a couple of edge cases that only show up once you're pushing real funds through a real wallet. Here's the breakdown, organized the way you asked for it.

## Onboarding

Worth being honest about the starting point so the timing doesn't read wrong: I inherited a project that already had its skeleton built — Rust/Axum backend, React frontend, Postgres, all wired together and running on fabricated data that was clearly labeled as fake. The job was wiring up five real APIs: RWA Data, Trading (aggregator quote/swap/approve), Transaction (gas price, on-chain simulation), Wallet (balances), plus an LLM agent for natural-language strategy parsing on top.

The first call that actually worked was RWA Data's `/dex/market/rwa/tokens` — nothing to complain about there, no signing required, filter to BSC and 448 real tokenized equities show up. The thing that actually ate time was signing, and not because HMAC-SHA256 is hard (wrote it once, backed it with three unit tests against the documented example, never touched it again for the rest of the project). It's one specific, easy-to-miss detail: the `/build` path prefix has to appear in both the string you sign and the actual request path you send. The docs do mention this — there's a footnote calling it out as the most common cause of signature failures — but when you're wiring up a dozen endpoints in one sitting and thinking about which *parameters* belong in the signature, not whether a *prefix* counts, it's easy to just miss it. And missing it gets you a completely generic invalid-signature error with zero diagnostic help, so you go through the usual stages of doubting your API key, your timestamp, your body serialization order, before it occurs to you to go back and re-read that footnote.

Rough sense of time: reading the auth docs and writing the signing client took about an afternoon, and roughly half of that afternoon was spent going in circles on that one prefix. Once it clicked, wiring up quote, simulate, approve-transaction, and swap was basically copy-pasting the same signing logic — never hit another auth-related error after that.

## Documentation issues

Two specific problems I can point at an exact page for.

**The parameter table for Trading API's `/aggregator/quote`.** `userWalletAddress` is listed as optional, with a footnote saying RFQ routes need it. The problem is that field really is optional for the non-RFQ routes, so the first time you skim the table it doesn't register as something to pay attention to. The failure mode isn't an error — it's a *silent* fallback to my own demo pricing formula. The app still looked like it was working, the numbers were plausible, it just wasn't a real quote. That's the worst kind of broken: nothing looks wrong. I only found the actual cause after adding a warning log around the call and seeing the real error text underneath: `userWalletAddress is required for RFQ (Ondo) quote`. This field should just be marked required for RFQ-style issuers like Ondo/bStocks, not buried as optional-plus-footnote.

**The response shape for `POST /aggregator/swap`.** This one went deeper. The documented example implies the transaction fields (`to`/`data`/`value`) sit at the top level, or inside a one-element array. The real response doesn't look like that at all — the actual transaction is nested under a `tx` key, alongside `executionMode` and `routerResult`. My parser kept returning nothing, with no API-level error at all — the call itself was a 200, I was just failing to parse it, and for a while I assumed I'd written the parsing code wrong. It took adding a log line to dump the raw JSON before I could see where the fields actually were. Anyone building a client straight from the documented example is going to hit this the first time they try to actually sign something real. Worth just publishing a captured raw response for endpoints like this instead of an idealized shape.

## API gotchas

A few things that made me stop and stare at the screen.

The one most likely to confuse someone: "insufficient balance" and "insufficient allowance" are two completely different reverts that look almost identical in text. `execution reverted: BEP20: transfer amount exceeds balance` means you're actually out of funds. `execution reverted: BEP20: transfer amount exceeds allowance` means you haven't approved enough yet. That part's not hard once you know it. What's harder is that `pre-transaction/simulate` only takes one transaction at a time, while a real swap is actually two transactions back-to-back — approve, then swap. If you simulate the swap on its own and the wallet hasn't approved the router yet, you'll always get an allowance revert, even though the approve transaction sitting right before it is about to fix exactly that. The simulator isn't wrong — it's honestly describing current on-chain state — it just has no visibility into the transaction you're about to send next. I got stuck on this across several real-signing attempts before I understood what was happening; the fix ended up being an application-level check: if the failure is specifically an allowance shortfall and there's an approve transaction queued ahead of it, don't treat that as fatal.

The other one: Ondo's RFQ route enforces a real **$5 minimum order size** (error code 40375). Not a problem by itself, except my own policy engine's per-trade cap also happened to be set at exactly $5. Two "reasonable" boundaries landing on the same number meant a trade at precisely $5.00 would pass or fail depending on a sliver of price drift between when I computed the size and when Binance evaluated it. Burned a fair bit of debugging time before I realized this wasn't my bug — it was two independent rules fighting each other at one unstable point.

On latency, pulling from actual accumulated call data (not a single test, a running median over several days of real traffic): `/aggregator/quote` sits around 123ms, `pre-transaction/simulate` around 183ms, a wallet balance lookup against a real non-empty address around 95ms. That's plenty fast for a dashboard refreshing in near-real-time. The LLM side (OpenAI, not Binance) is noticeably slower — single-turn parsing lands around 2.5–3.6 seconds, which makes sense since it's doing actual reasoning rather than a lookup, but worth flagging if anyone's expecting agent endpoints to feel as fast as the REST ones.

One more edge case, more funny than important: I tested the Wallet API's balance lookup against the well-known BSC burn address out of habit, expecting it empty. Got back over a hundred tokens — dead memecoins, one literally named "Web3AI," something called "屬蛇coin." Not a bug, just a reminder that the endpoint is reading real chain state, not a curated allowlist.

## AI stack feedback

Being straight about this one: **I didn't end up using Wallet Skills or the Agentic Wallet**, and that was a deliberate call after investigating, not something I just gave up on.

Binance Agentic Wallet looked at first like exactly what "real signing" needed. It took some doc-reading to realize it's a completely different shape of product from RWA Data/Trading/Transaction — it's an MPC keyless wallet tied to a person's own Binance account, authorized via QR-code login to the Binance App, operated through a Skill installed for an AI assistant (`npx skills add binance/binance-skills-hub/skills/binance-web3/binance-agentic-wallet`) and driven by natural-language conversation. The whole design assumes a one-to-one relationship: one person, one AI assistant, operating that person's own wallet.

What I was building is a backend serving arbitrary users — there's no documented way for a backend to call Agentic Wallet "on behalf of" a signed-in user to sign and broadcast something. If you actually want to use that path, it has to be the AI agent itself sitting on the user's own machine, with the Skill installed, acting directly on that user's own logged-in account — never going through my web backend at all. So real signing ended up using the most direct approach instead: the backend only builds unsigned calldata and runs one on-chain simulation to confirm it won't fail, and signing/broadcasting is handled entirely by the user's own connected browser wallet via `eth_sendTransaction`. The backend never touches a private key, start to finish.

This isn't a knock on Agentic Wallet's design — for the use case it's built for (a person plus their own AI assistant), it's a reasonable choice. It would just help to say that more explicitly up front — "this is for individual AI operators, not something a multi-tenant app backend calls" — so people don't burn time reading docs and writing test code to figure that out themselves, the way I did. Same reason I didn't end up touching the CLI; it's the same architecture mismatch.

## Tokenized-stock specifics

**Liquidity depth.** This project ended up using 24h volume as a stand-in for liquidity, not a real depth curve — partly laziness, since I never wired up `top-liquidity` or similar, but also because the endpoints actually in use (RWA Data, aggregator quote) don't return depth data directly; getting a real curve means stitching together an extra call. `priceImpact`, on the other hand, comes straight back from the aggregator quote and it's honest — the numbers line up with what you actually get quoted.

**Behavior outside trading hours** is the finding I'd flag as most worth including here. Several assets (KLAC, CVNA, SOXS, ENLV are the ones I dug up from historical snapshots) show an enormous gap between on-chain price and reference price while the underlying market is closed — KLAC peaked at a 900% gap in the recorded history. My first reaction was that I'd caught a huge move. Pulling a wider time window showed the gap was actually *flat* — not the price running away, the **reference price had simply stopped updating**. On-chain trading kept going 24/7, the two numbers drifted apart and then just sat there, because a dead gap doesn't converge back on its own. That's a completely different situation from a real premium that moves and then reverts — IBM and QCOM, pulling the same historical data, both show that kind of genuine back-and-forth that resolves. But looking only at the current gap number, the two situations are indistinguishable. That's a real trap for anyone trying to do anomaly detection on this data: you need some way to tell whether the reference price is actually alive, not just how big the gap looks right now.

**bStocks / Ondo / xStocks in practice** turned into an accidental finding too: the code has logic to label an "xStocks" issuer, but scanning all 448 currently tracked assets, **xStocks never actually showed up once**. Everything is either Ondo (442 assets, ~99%) or bStocks (46 assets, ~10%). In other words Ondo is effectively the default, always-there issuer, and bStocks is the minority. The practical consequence: that $5 Ondo minimum I mentioned earlier doesn't have an escape hatch for most assets — only the 46 tickers that happen to carry bStocks coverage (NVDA, AMD, COIN, GOOGL among them) let you dodge it by switching issuer. The other ~90% just have to live with Ondo's rules.

## How I'd redesign it

If I were rebuilding this so someone gets a successful call right after signing in, three things:

First, **signing shouldn't be something developers hand-write at all**. Put a tool right in the docs page: paste your API key, pick an endpoint, get back a correctly signed, `/build`-prefixed curl command you can copy and run. Right now the docs describe the signing algorithm in prose and leave every integrator to reimplement it — the algorithm itself isn't hard, what's hard is that you never know what you got wrong, because the error message only ever says invalid signature, never whether it was the prefix or the body serialization order.

Second, **example responses for transaction-building endpoints should be real captured data, not idealized shapes**. The nesting in `/aggregator/swap` is exactly the kind of thing that, once the docs and reality disagree, leaves a developer with no recourse except adding their own logging and dumping raw JSON to see what's actually there. I did that myself, but not everyone's going to think to, and honestly it shouldn't be their job in the first place.

Third, **a funded testnet environment specifically for the trading flow** — quote → approve → simulate → sign → broadcast. The gotchas that actually cost the most time here (allowance vs. balance, whether to let the wallet pick its own gas price) only show up once you're using a real wallet signing and sending something real. Right now "sending something real" means spending real money, which is an unnecessary barrier for anyone who'd otherwise be happy to exercise the whole flow early.

## Feature requests

- An official SDK (TypeScript, or at least a Rust crate) that wraps the signing logic, so nobody has to hand-roll HMAC plus the `/build` prefix again.
- A combined simulate-and-classify-the-failure endpoint, instead of making callers parse the free-text `failReason` string and guess which category it falls into.
- Let `pre-transaction/simulate` accept a *sequence* of transactions, not just one — approve-then-swap is a dependency the API should understand natively instead of pushing that special case onto every caller's application layer.
- Some way to query reference-price freshness directly through the API — a timestamp field, or a plain `stale: true/false` would do. Right now the only way to tell is comparing historical snapshots yourself, and that exact gap (reference price going stale while the market's closed) was the single biggest trap in this whole integration.
- A documented path for a multi-tenant backend to drive the Agentic Wallet signing flow on behalf of a signed-in user, instead of scoping it to "individual AI operator on their own account" only.
