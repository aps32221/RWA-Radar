# RWA Radar × Binance Web3 API 開發者體驗報告

*RWA Radar — 代幣化股票異常監控，BNB Hackathon*

這份不打算寫成公關稿。短版結論：簽章機制一旦踩過一次坑之後就很穩，真正燒時間的從來不是密碼學本身，而是兩三個文件沒講清楚、只有拿真錢包、真資金去跑過一輪才會冒出來的邊緣案例。下面是逐項的細節，照你們要的七個項目寫。

## 入門體驗

先說清楚起點，免得時間感失真：接手的時候專案骨架已經搭好（Rust/Axum 後端、React 前端、Postgres），資料全部是假的、而且介面上標得清清楚楚是 demo。要做的事情是把五支 API 真正接起來：RWA Data、Trading（aggregator quote / swap / approve）、Transaction（gas price、鏈上模擬）、Wallet（餘額查詢），外加一個 LLM agent 做自然語言策略解析。

第一個打成功的呼叫是 RWA Data API 的 `/dex/market/rwa/tokens`，這顆沒什麼好抱怨的——不用簽章，篩一下 BSC 鏈，448 檔代幣化股票直接進來。真正卡住的是「簽章」這一步，而且卡住的不是 HMAC-SHA256 本身（寫一次、對著官方範例補三個單元測試、後來整個專案期間沒再碰過），是一個很容易漏看的細節：`/build` 這個路徑前綴，必須同時出現在「你拿去簽章的字串」跟「你實際打出去的 request path」兩個地方。文件裡其實有講，用一個註腳的方式提到這是最常見的簽章失敗原因——但你同時在串十幾個端點、腦子裡想的是「這個參數要不要塞進簽章」而不是「這個前綴算不算在簽章裡」，真的會漏掉。漏掉的下場是一個完全通用、沒有任何額外提示的 invalid signature，你會先懷疑自己 API Key 貼錯、懷疑 timestamp 對不上、懷疑 body 序列化順序不對，繞了一圈才想到回去重讀那個註腳。

粗略的時間感：認證之前的讀文件、寫 client，大概一個下午，但這個下午有一半時間就耗在上面那個前綴上。一旦抓到，後面接 quote、simulate、approve-transaction、swap 幾乎是複製同一套簽章邏輯貼上去，沒再出過任何認證相關的錯誤。

## 文件問題

兩個具體、可以直接對應到頁面的問題。

**Trading API `/aggregator/quote` 的參數表。** `userWalletAddress` 被標成 optional，附一個註腳說 RFQ 路由需要它。問題是這個欄位對非 RFQ 的一般聚合報價確實是真的可有可無，所以第一次掃過參數表完全不會特別在意它。後果不是報錯，是「安靜地」退回我自己寫的 demo 公式——畫面看起來一切正常，數字也合理，只是不是真的報價，這種「看起來沒壞但其實沒在工作」是最難抓的一種。我是後來自己加了一行 warning log 才看到背後的真正錯誤訊息：`userWalletAddress is required for RFQ (Ondo) quote`。建議這個欄位對 Ondo/bStocks 這類 RFQ 發行商應該直接標成 required，而不是用一個容易被忽略的 optional + 註腳帶過。

**Trading API `POST /aggregator/swap` 的回應格式。** 這個踩得比較深。文件範例給的回應結構，交易欄位（`to`/`data`/`value`）看起來是在最外層，或者包在一個單元素陣列裡。實際打出來的回應完全不是這樣：真正的交易內容包在一個 `tx` 欄位底下，外面還包了一層 `executionMode`/`routerResult`。我原本的 parser 一直回傳空值，而且沒有任何 API 層級的錯誤——呼叫本身是 200，只是我自己解析失敗，查了半天以為是自己哪裡寫錯。直到加了一行 log 把完整原始 JSON dump 出來，才看到欄位實際藏在哪。這個落差如果照著文件範例寫 client，第一次真的要簽署送出交易時一定會卡在這裡；建議這類端點的文件直接貼一份真實呼叫拿到的 raw response，不要只給示意結構。

## API 陷阱

幾個會讓人原地愣住的狀況。

最容易搞混的一組是「餘額不足」跟「額度不足」這兩種 revert，字面長得很像，意思完全不同：`execution reverted: BEP20: transfer amount exceeds balance` 是真的沒錢；`execution reverted: BEP20: transfer amount exceeds allowance` 是還沒 approve 夠的量。這本身不難懂，難的是 `pre-transaction/simulate` 這顆模擬端點一次只吃一筆交易，而一次真正的 swap 其實是「先 approve、再 swap」兩筆接力送出。如果你拿 swap 單獨去模擬，而這個地址剛好還沒對這個 router 做過 approve，模擬結果一定是 exceeds allowance——即使緊接著那筆 approve 馬上就會把這個狀態改掉。模擬本身沒有錯，它誠實反映「現在」的鏈上狀態，只是它沒辦法知道「接下來」要送出的那筆交易會改變這個狀態。這個坑我自己是真的連續被卡了好幾次真實簽署才搞懂，最後的解法是在應用層自己判斷：如果失敗原因明確是 allowance 不足、而且確實有排一筆 approve 在這筆交易前面，就不當成致命錯誤擋下來。

另一個是 Ondo 的 RFQ 路由有一個真的存在的 **$5 最低下單金額**（錯誤碼 40375）。這本身沒什麼，問題是我自己的風控策略一開始也剛好把單筆上限設在 $5——兩個「合理」的邊界卡在同一個數字上，導致剛好 $5 的交易會不穩定地過關或失敗，差別只在下單那一刻跟報價計算那一刻之間一點點的價格漂移。浪費了不少除錯時間才看懂這不是我這邊的 bug，是兩條規則自己打架。

延遲的部分，用目前累積的真實呼叫數字（不是單次測試，是連續跑了幾天的中位數）：`/aggregator/quote` 約 123ms、`pre-transaction/simulate` 約 183ms、wallet 餘額查詢（查一個真的有東西的地址）約 95ms。對一個要即時刷新的 dashboard 來說這個速度算夠用。LLM 那端（OpenAI，不是 Binance 自己的）明顯慢很多，單輪解析落在 2.5–3.6 秒之間，這個合理，畢竟是在做推理不是查表，只是提醒一下：如果有人預期 agent 端點跟一般 REST 端點一樣快會落空。

還有一個算邊緣案例但挺有意思的：Wallet API 的餘額查詢，我拿知名的 BSC 燒毀地址測過——按理說應該是空的，結果回來一百多個 token，各種死掉的 memecoin、一個叫「Web3AI」的，甚至有個「屬蛇」幣。不是 bug，只是提醒我這顆 API 真的在讀鏈上真實資料，不是在查一份乾淨的白名單。

## AI 堆疊回饋

這題要老實講：**最後沒有用上 Wallet Skills 或 Agentic Wallet**，而且是調查過之後主動決定不用，不是沒試過就放棄。

Binance Agentic Wallet 一開始看起來正好是「真實簽署」這塊要的東西，花了些時間讀文件才發現它跟 RWA Data／Trading／Transaction 這幾支 REST API 完全是不同形狀的產品：它是一個 MPC keyless 錢包，私鑰綁在使用者自己的 Binance 帳號上，操作方式是透過 QR code 登入 Binance App 授權；介面是裝給 AI 助理用的 **Skill**（`npx skills add binance/binance-skills-hub/skills/binance-web3/binance-agentic-wallet`），用自然語言對話下單。這個設計假設的是「一個人、一個 AI 助理、操作這個人自己的錢包」這種一對一關係。

我在做的是服務任意使用者的多租戶後端——沒有任何文件化的方式能讓後端「代表某個登入中的使用者」去呼叫 Agentic Wallet 簽署並廣播交易。這條路真的要走，得是 AI 代理人本身（例如裝了對應 Skill 的 AI coding assistant）直接坐在使用者自己的機器上，對著使用者自己登入的帳號操作，完全不經過我這邊的網頁後端。所以最後真實簽署這塊改成最直接的做法：後端只負責組出未簽章的 calldata、跑一次鏈上模擬確認不會失敗，簽署跟送出完全交給使用者連接的瀏覽器錢包（`eth_sendTransaction`），後端自始至終不碰私鑰。

這不是在說 Agentic Wallet 設計得不好——對它鎖定的那個情境（個人 + 自己的 AI 助理）應該是合理的選擇。只是如果文件能更早講清楚「這是給個人 AI 操作者用的，不是給多租戶應用後端呼叫的端點」，我可以省下讀文件、寫測試去確認這件事的那段時間。CLI 的部分是同一個原因沒用上，架構本來就不合。

## 代幣化股票細節

**流動性深度。** 最後這個專案用 24h volume 當流動性的代理指標，不是真的深度曲線——老實說有偷懶的成分，因為沒把 `top-liquidity` 這類端點另外串進來，但也是因為手上在用的這幾支端點（RWA Data、aggregator quote）本身不直接回傳深度資料，要湊出一條真正的深度曲線得另外拼一支呼叫。`priceImpact` 這個欄位倒是直接從 aggregator quote 回來，用起來很老實，數字跟實際成交報價對得上。

**休市時段的行為**，這是這次測試中我覺得最值得寫進報告的發現。有幾檔資產（KLAC、CVNA、SOXS、ENLV 是我自己查歷史快照挖出來的例子）在市場休市的狀態下，鏈上價格跟參考價格的差距會瞬間變得非常誇張——翻資料庫裡存的歷史快照，KLAC 甚至出現過 900% 的落差。一開始以為真的抓到大行情，後來把時間窗拉長看，才發現這個落差是「持平」的：不是價格真的跑開了，是**參考價格停更了**，鏈上交易照常 24 小時在跑，兩邊就這樣越拉越開，而且因為差距是死的，不會自己收斂。這跟真正「鏈上溢價在波動、之後回歸」的訊號完全是兩回事——同樣翻歷史資料，IBM、QCOM 這幾檔波動明顯的資產就看得到溢價真的會縮回去——但如果只看當下那個 gap 數字，兩種情況長得一模一樣。這對任何要做異常偵測的人都是個大坑：需要某種方式分辨「這個參考價是不是還活著」，而不是只看 gap 絕對值有多大。

**bStocks / Ondo / xStocks 的實務差異**，這個也是意外發現：程式碼裡有處理 xStocks 這個發行商標籤的邏輯，但實際把目前追蹤的 448 檔資產全部掃過一輪，**xStocks 一次都沒有真的出現過**——全部只有 Ondo（442 檔，約 99%）和 bStocks（46 檔，約 10%）。換句話說 Ondo 幾乎是預設、永遠在的那個發行商，bStocks 反而是少數。這件事的實際影響是：前面提到 Ondo 的 $5 最低下單量問題，對大多數資產其實沒有退路可選——只有剛好在那 46 檔 bStocks 名單裡的資產（NVDA、AMD、COIN、GOOGL 這些算在裡面）才能靠換發行商閃掉這個限制，其餘九成資產只能硬著頭皮啃 Ondo 的規則。

## 重新設計建議

如果要重新設計這個平台，讓人一登入就能打出第一個成功的呼叫，我會做三件事。

第一，**簽章這一步根本不該讓開發者自己寫**。文件頁面直接給一個小工具：貼上你的 API Key，選一個端點，產生一條已經簽好章、帶對 `/build` 前綴、複製貼上就能跑的 curl 指令。現在的做法是用一段散文描述簽章演算法，讓每個整合者自己重新實作一次——演算法本身不難，難的是「永遠不知道自己哪裡做錯了」，因為錯誤訊息只會告訴你 invalid signature，不會告訴你是前綴漏了還是 body 序列化順序不對。

第二，**交易相關端點的範例回應要貼真實資料，不要貼示意結構**。`/aggregator/swap` 這種巢狀結構一旦文件範例跟實際回應對不上，開發者唯一的除錯手段就是自己加 log、自己把原始 JSON dump 出來看——這件事我自己做了，但不是每個人都會想到要做，而且這本來就不該是開發者的責任。

第三，**給一個帶假資金的測試網環境，專門給交易流程用**（quote → approve → simulate → sign → broadcast）。這次踩到的幾個最花時間的坑（allowance vs balance、gas price 要不要讓錢包自己估）都是只有「真的用真錢包、真的簽、真的送出」才會冒出來的——而目前的設計下，「真的送出」就代表要動用真錢，這對願意儘早把整條流程跑過一輪的開發者是個不必要的門檻。

## 請求功能

- 官方 SDK（TypeScript 或至少一個 Rust crate），把簽章邏輯包起來，不要讓每個整合者重新實作一次 HMAC + `/build` 前綴。
- 一個「模擬 + 失敗原因分類」合併在一起的端點，不要讓開發者自己去 parse `failReason` 的自由文字字串猜它屬於哪一類問題。
- 讓 `pre-transaction/simulate` 能接受「一組交易序列」而不是只能單筆——approve 接 swap 這種前後依賴的狀況應該由 API 自己處理，不該要呼叫方在應用層自己加特判。
- 參考價格的「新鮮度」要能透過 API 直接查到，一個 timestamp 欄位或一個明確的 `stale: true/false` 都好——現在只能靠自己比對歷史快照去猜，而這個落差（休市時參考價停更）正是這次測試踩到最大的一個坑。
- 給多租戶後端一條文件化的路，能夠代表登入中的使用者走 Agentic Wallet 那套簽署流程，而不是把它限定在「個人 AI 助理操作個人帳號」這一種情境。
